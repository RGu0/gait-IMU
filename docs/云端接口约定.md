# 云端服务接口约定 —— 仓库侧入口

**这份文件不是约定本身，是指路。** 约定有两卷，都在共享库
`.project-context/documents/`，因为它们是需求侧文档而非代码：

| 卷 | 路径 | 地位 |
|---|---|---|
| 抄录卷 | `.project-context/documents/云端服务接口约定_抄录卷.md` | **既有事实的转录** —— 足压平台已跑通的实现，逐条带文件行号。**不需要服务方确认**，可直接照着写客户端 |
| 待确认卷 | `.project-context/documents/云端服务接口约定_待确认卷.md` | **提案** —— 抄不到的两条半。**服务方签字前不得当作约定** |

两卷当前均为 **v0.2**（2026-09-07）。版本只写在各文档自己的修订记录里，**文件名不带版本**，
所以这两个路径不会随升版失效。来源：RAY-353，需求修订 R1。

## 为什么仓库里要留这一页

写客户端的人在仓库里干活，不会去翻共享库；而这两卷的**地位差别**（哪些能直接
写代码、哪些会被推翻）恰恰是最容易读漏的东西。把入口留在这里，是为了让
「照着抄录卷写」和「等待确认卷签字」这两件事不会被混成一件。

## 开工前必须知道的三个坑

1. **`E-SYN` 不是 `E-SYNC`。** 服务端 `E-SYN-409` 是*分段摘要冲突*；本仓库
   `E-SYNC`（`src/gait/app/contract.json`）是*双足同步残差*。按前缀匹配会把一次
   上传冲突显示成算法故障。**上传类错误在本仓库归 `E-NET`。**

2. **服务端错误码不能透传到界面。** 服务端是 `E-<3字母>-<3位数>`（数字即 HTTP
   状态），本仓库是四位数 + 域内号段，`errors.check_code()` 会直接拒。必须在
   客户端内部做映射，由 sidecar 出成品文案（RAY-248 验收第二条）。
   **`contract.json.codes` 里目前一个 `E-NET` 码都没有** —— 待确认卷 §2.2 给了
   取值与文案，**补登由消费它们的 Issue 在实现时做**，不属 RAY-353。

3. **两套凭据的方向与足压平台相反，但 Foundation 已经解决了。** 足压平台把操作员账号
   登录得到的 token 直接当数据面凭据；PRD §19 / FR-01 要求数据面只认终端凭据、
   操作员账号只回答「谁在操作」。**照抄足压平台会违反 FR-01。**

   但 techflex-cloud-foundation 用**类型**把两者分开了——`InstallationPrincipal`
   （终端）与 `TenantPrincipal`（操作员）互不含对方的字段，分离由类型保证。
   **所以这套机制不用自己发明**，gait 只需定线格式（Foundation 有意不定 HTTP 路由与 DTO）。
   详见待确认卷 §1.1b。

   **发布这一层于 2026-09-07 解除**：Foundation 当天发布 v0.2.0，`iam.py` 与
   `device_trust.py` 都在里面。

   **2026-09-08 又去掉了两层。** 用户当天拍了四条：RAY-323 那三条产品决定（断网可凭
   限期票据开工、票据 7 天、操作员身份不进会话元数据由服务端审计 —— 见 RAY-323 的
   **R1**），以及**服务端建在 Foundation 上，跟足压平台一路**（RAY-443）。

   **于是只剩一层：线格式要服务方签字。** Foundation **有意不定 HTTP 线格式**
   （product routing 与 DTO 归应用），所以拍了「建在 Foundation 上」并不等于线格式定了
   —— 那永远是本仓库自己的事。可以先照提案写客户端 + 假服务端测（RAY-355 / RAY-322
   就是这么做的），但**契约翻面前需要那一层落定**。

   以上是 2026-09-08 的记录；**Issue 的现状以 Linear 为准**。

## 维护

改这两卷时**同时**过一遍 `.project-context/documents/派生文档索引.md`（v1.1 起
已登记它们，v1.2 起两卷都在 v0.2）。

注意三条上游、两种触发条件：

| 文档 | 上游 | 什么会让它说错话 |
|---|---|---|
| 待确认卷（索引 A6，收录） | PRD §19 / FR-01 **+ techflex-cloud-foundation** | PRD 改了；或 **Foundation 升版**（RAY-443 起它是带版本的依赖，升版会让 lint 变红，见下）|
| 抄录卷（索引 §2.2，排除） | 足压平台的代码 | 那边改了 `shared/contracts/cloud.py` 或 `cloud/api/errors.py` |

**两份都有一条上游是「另一个仓库的代码」** —— 索引 §4 **D6** 记的就是这个缺口。
RAY-420 已把它的**源码那一半**接上闸：`tools/upstream_refs.json` + `check_upstream_refs.py`，
在 `./dev lint` 里跑。**RAY-443 之后两条上游不再同形**，各有各的钉法：

| 上游 | 钉法 | 缺席时 |
|---|---|---|
| 足压平台（11 个文件） | 逐文件 sha256，比对本机同级目录里的仓库 | 报「未能核对」，不红 |
| **Foundation**（3 个文件） | **不逐文件钉** —— `pyproject.toml` 给 release 资产 URL，`uv.lock` 记 wheel 的 sha256（`--locked` 每次安装都校验）；声明里记版本，**升版就红** | 没有「缺席」这一档：锁文件在库里，CI 也读得到 |

**为什么 Foundation 那一栏更强。** 它是 RAY-420 说的方案 B 落地：外部上游变成**带版本的
依赖**后，内容漂移在这里已经不可能（哈希每次安装都验），而**升版变成一次会变红的显式
事件** —— 报错里点名逐行转录它的那几份文档，逼人回头重读，而不是让一行 URL 的 diff
悄悄作废两卷的内容。

（一处更正：本页此前推测「把 `url =` 换成 `path =` 会让 uv.lock 不再记哈希」——**实测不是**，
`path` 来源照样记。所以那条守卫改成了守升版，那才是真会静默出错的地方。）

声明完整性那一层对两类上游都跑：**仓库文件里引用到的上游文件都得在声明里**，CI 也查。

**够不到的地方，照实说：** 两卷在云端库里，不在 git，CI 看不见它们那 34 处引用 ——
足压平台那一栏只有本机跑 `./dev lint` 才核得到（Foundation 那一栏不受此限，它靠锁文件）。
而 **Issue 状态漂移查不了**（脚本拿不到 Linear 凭据）：RAY-417 咬到的恰恰是这一类，
上游源码一字未改，变的是「那条阻断还成不成立」。所以照着这两卷写代码前，
**结论仍要自己复核一遍**。

## 写法规则：写发生过的事，不写现在的状态

上面那条「查不了」不必全靠复核 —— **大半可以在写的时候就消掉**。

对比同一件事的两种写法：

| 写法 | 会不会变假 |
|---|---|
| ~~`iam.py` 在 v0.2.0 里（RAY-412 已 Done）~~ | **会**。括号里是现在时断言，上游一改就假，而这边不会知道 |
| Foundation 于 **2026-09-07** 发布 v0.2.0，`iam.py` 在里面 | **不会**。它是既成事实，日期把它钉在时间轴上 |

规则两条，缺一不可：

1. **带日期。** 一个带日期的观察永远为真 —— 它只是可能**过时**，而过时与说假话是
   两回事：读者看见日期就知道要不要重查，看见「已 Done」则会直接采信。
2. **给权威指针。** 状态的权威在 Linear，不在这里。写「以 RAY-323 的当前状态为准」，
   比在这里复述一份会腐烂的副本强。

**为什么不做成检查。** 试过量：仓库里 1036 处 `RAY-xxx` 引用，同行带状态词的 21 处，
其中**跨项目的只有一处**；其余 20 处说的是本仓库自己的 Issue，且大半是
「尚未实现（RAY-208）」那一类 —— 那些 `contract.json` 已经在管，
`protocol.unimplemented()` 会拒绝一个已实现的能力，**已有真闸门**。为一处现存暴露
加一条会误报 20 次的 lint，只会训练人去绕它。

**真正能查这件事的是完成闸门，不是 lint** —— 它跑在一个有 Linear 的会话里，而 CI
没有。那一半已按 RAY-376 的先例移交治理侧 —— **RAY-436**（`git-worktree-linear-workflow`），见 RAY-420。
